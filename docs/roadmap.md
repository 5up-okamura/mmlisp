# MMLisp Roadmap

What is still ahead. Finished phases are one line each; the language and the
driver as they stand are described in `docs/language.md` and `docs/driver.md`.

## Shipped phases

- **Phase 0 — spec and authoring validation.** Language subset, IR and the
  first MMB draft; v0.1 frozen at tag `v0.1-candidate`.
- **Phase 0.5 — editor tooling.** VS Code TextMate grammar (`mmlisp-syntax/`)
  and format-on-save.
- **Phase 1 — web authoring environment.** `live/` is the working environment:
  browser compiler, Nuked-OPN2/PSG playback, hot-swap on edit, transport and
  loop handling, source-mapped playhead, parameter panels, file I/O and the
  value-editing UI.
- **Phase 2 — compiler and format stabilization.** Parser, IR, MMB writer and
  the version/compatibility rules; output is deterministic.

## Phase 3: Driver (MMLispDRV)

The driver plays MMLisp scores in an SGDK build: a C sequencer on the 68000 and
a PCM/chip-write engine on the Z80 (`docs/driver.md`; `drv/`). Verified on the
host and in a patched headless BlastEm.

Landed:

- **Format and reference** — MMB v0.3 with the opcode/target tables
  (`docs/mmb.md`, `docs/opcodes.md`); `drv-player.js` is the executable spec
  and the live app's MMLispDRV backend.
- **Sequencer** — `drv/68k/mmlispseq.c`, byte-identical to `drv-player.js` on
  the gate corpus (`npm run c-gate`): notes, loops, CALL/RET, tempo, sweeps,
  macros, CSM, FM3 independent-OP, val slots, sound effects, PCM commands,
  priming at load.
- **Engine** — three pair-transport Z80 images, one per PCM voice count
  (1–3 voices at 14,376 / 10,112 / 6,653 Hz, loops, 6 dB levels), each DAC
  clock from its own instruction stream, generated by `drv/engine/`. A score
  picks its image with `(def-score :pcm-voices N)`; loop points move while a note
  plays.
- **Host** — `drv/sgdk/` (one bus grab a frame from VSync) and
  `tools/install-sgdk.mjs`; real scores on all three images played on BlastEm
  with every write and DAC byte graded against the engine model.
- **PAL** — a score is baked for one standard and the MMB header says which
  (driver.md §3.3).
- **Browser** — the live editor's IR preview plays PCM through the driver's own
  voice model and engine, on the bank an export ships.

Open (the limits themselves are `driver.md` §11 — keep the two in step):

1. **A hardware run.** The images sit at a 100% work ceiling and have only
   been graded in the JS machine and on BlastEm.
2. **Wire budget.** 960 pairs a second. The opening setup is primed at load,
   but a mid-song change still has to fit through it.
3. **Mid-song voice changes** — VOICE_SET bodies in the sample-bank ROM, so a
   voice change is one pair instead of the ~30 register writes a channel costs
   today.
4. **Several scores resident at once** (DJ-style transitions, driver.md §2.3;
   `.claude/memory/driver-decisions.md` §11). Today one score is resident and a
   bundle's songs share one sample bank.
5. **PAL PCM pitch and SE rough edges.** A single-bank PAL score's samples are
   baked at the NTSC DAC rate (the multi-bank images have PAL rates of their
   own). A PCM SE restarts a looping BGM note from
   the sample's head rather than where it was, and a sweep in flight on a
   stolen channel is lost rather than resumed. Effects themselves are
   `def-se`, written once and given to every song by the bundle
   (language.md §9.3).
6. **A small Z80-only build** — sequencer and engine both on the Z80, for a
   game that cannot spare the 68000. Speculative; the measurements that moved
   the sequencer off the Z80 are in `.claude/memory/driver-decisions.md`.

## Phase 4: Integration and Demo

The end-to-end path works: `install-sgdk.mjs` builds a scratch SGDK project
from a score or a bundle, and `drv/sgdk/example` is a playable demo of the
interactive surface — BGM, FM/PSG/PCM effects at priorities, live value slots,
song switching. What remains is breadth: more game-scene mappings worth
shipping as examples, and a hardware-verified reference build.

## Language: what is still open

Compile-time eval is the centerpiece of the current language, and its
foundations have landed. The channel body is an implicit quasiquote (bare atoms
are literal note data, parenthesized forms are the compute boundary), eval is
compile-time only and bakes to static data, and `$slot` / `def-val` remains the
sole runtime-varying path. Shipped: scalar and curve arithmetic, `let`, `note`,
`ticks`/`frames`, `:seed`, signal materialization (language.md §7); on the
driver, the generic shadow read and value machine (left-linear `$slot`
expressions at event ticks), additive `:pitch+`/`:semi+`, the scaled-macro
depth knob and slot-fed sweep endpoints. All four sampling tiers (compile,
tick, note-on, frame) have driver support and gates.

Still ahead:

- **Slot-fed macro-curve params** — `:from`/`:to`/`:rate`/`:len` on a macro
  curve, and a sweep's `:len`, bake to their init values today.
- **The compile-time shadow fold** (parked) — folding static bases at compile
  time instead of emitting the arithmetic.
- **`if` / `for` / def-functions**, and what eval enables past them:
  algorithmic composition, parametric phrases as real functions, signal
  composition (`(+ (sin) (saw))`, `(* env lfo)`), curves as a standard library.
- **The behaviour questions** where the driver and the editor disagree, and
  the larger judgment-free items, are listed in
  `.claude/memory/language-open.md` — several need a decision before they can
  be implemented.

## mucom88 Importer

Converts a mucom88 `.muc` song (PC-8801 / YM2608 OPNA) to MMLisp source.
Implementation: `live/src/import-mucom.js` (+ `mucom-pcm.js` for the ADPCM
bank). Pipeline: `.muc` → ops → MMLisp text → (compiled by the normal
toolchain).

Implemented: FM A–C / H–J → `fm1`–`fm6`, SSG D–F → `sqr1`–`sqr3` (the notes
an SSG part plays with noise on go to `noise`), ADPCM K → `pcm1`; notes,
lengths and ties on mucom's clock grid; loops, breaks and the last `L` as the
loop point (a part without `L` plays once); key shift `K`/`k`; detune `D`
(also relative `D n+`); `v`, `)`/`(`, `V`; `q`; reverb `R`; register writes
`y`; SSG `E` envelopes and `@n` presets; `P`/`w`; inline, `@%` and `.dat`
voices; macros; echo; portamento, hardware and software LFO; both tempo
commands. A song using part J and the drums keeps J commented out: fm6 is the
DAC while PCM plays.

What the importer reproduces from the driver rather than approximates:

- **Loop passes.** mucom compiles a loop body once (octave, `l`, `K` are
  baked, as in MMLisp) but `)`/`(`, `D n+`, `q` and ties are driver commands
  that act on every pass. A loop whose passes would differ — and one tied into
  or out of — is written out pass by pass, across lines too.
- **Software LFO and detune** add to the raw pitch word (F-number with block
  carry; SSG o1 period), so their cents depend on the note: a sweep such as
  `M1,1,-9,250` is drawn per pitch class from the exact curve.
- **Levels.** mucom writes every carrier TL from `FMVDAT[v+4]` and ignores the
  voice's own, so voices are emitted with carrier TL 2 (the v15 value). A level
  change during a tie moves `:vol`; reverb's tail is a tied note at `:vol`.
  SSG volume steps are 3 dB (PSG `:vel` 2 dB), and its envelope lands linearly
  on them, so each envelope is drawn per `:vel`.
- **Tempo** is `BPM = 832000 / ((256 − t) × C)` (Timer-B 2304 cycles at
  7.9872 MHz, one clock per two overflows), kept to two decimals; `T` goes
  through the Timer-B value it compiles to.
- **ADPCM pitch**: o1 c plays at Delta-N `0x49BA+200` = 16143.6 Hz, the bank's
  labelled rate.
- **Drum length**: the driver stops the ADPCM at key-off (q point, next note
  or rest), a MMLisp shot plays to the end — so each sample's `:frames` is cut
  to the longest stretch the song plays of it. If the drums still overflow the
  32 KB bank at one voice's 14.4 kHz, the import sets `(def-score :pcm-voices 2)` or
  `3` for the lower rate they fit at. When none fits — a long melodic sample
  baked once per pitch played, like THE SCHEME's guitar — the costliest sample
  is dropped (its notes rest, with a warning) and the search starts over.

Hardware limits, kept visible as warnings: SSG notes below A2 play an octave
up (the PSG's floor); SSG levels under −30 dB hold at `:vel 1`; one noise
channel, so only the first part using noise keeps it; SSG reverb rings
without its level drop.

### Verification

Checked against the real driver: mucom88 (`github.com/onitama/mucom88`, the
CLI built from `src/` with `OS_SDL=0`) renders each song to VGM (`-x -o <name>.mub
-b <name>.vgm`; it reads `.muc` as UTF-8 off Windows), and the YM2608 register
log is compared with the import's `IRPlayer.captureRegisterLog` — per part:
keyed state, pitch, carrier/PSG level; PCM key-ons and sample. On the songs
checked (ACTRAISER stg001, BOSCONIAN bos010/011, MISTY BLUE hrock1, BARE
KNUCKLE stk004/013 and bare03/04) FM parts match 98–100 % of sounding frames
in pitch (92 % for one part made of long sweeps, fitted with linear
segments), PCM key-ons all match.

### Track alignment

Every part of 42 / 46 reference songs loops in the same period. The others:
`stk023`, `bare12`, `slp010` end in short silent loops of different lengths
(as in mucom); `bare21` drifts 16 ticks a loop — a loop body whose clocks are
not a whole number of ticks at `C112` replays its rounded lengths (lengths are
dithered note to note, which a replayed body cannot carry).

### Not yet imported

- **`S` FM3 slot detune** (13 songs): maps onto `fm3-1`–`fm3-4` with a
  per-operator `:pitch`, `:vel` on the carriers only.
- `s` key-on revise (alternating length offset).
- Part **G** rhythm: its sounds are the OPNA's rhythm ROM — no data to import.

### Reference

- Driver source (authoritative): `github.com/onitama/mucom88` →
  `pc8801src/ver1.2/{muc88,music,msub}.asm`. Command table: `msub.asm`.
- Lengths: `floor(C / len)` clocks, each clock = `384 / C` ticks (PPQN 96).
- License: mucom88 is CC BY-NC-SA 4.0; the importer only reads the format and
  bundles no mucom88 code/data (see README).

## Future Vision (post-MVP ideas)

### A patch ecosystem on `import`

`(import "path")` already merges another file's defs at compile time
(language.md §9.2). The ecosystem idea keeps that surface and adds sources:

```lisp
(import "reverb"    :from :stdlib)
(import "dx7-brass" :from :patches)
(import "my-arp"    :from "https://mmlisp.community/patches/okamura/arp01")
```

- Resolution stays at compile time and folds into IR — no runtime dependency.
- Patch types: **function effects** (delay, arpeggiator, LFO) as scheduler-layer
  code, and **FM voices** as a canonical voice asset schema.
- Version pinning (`@1.2.3`) is required for reproducibility.

### Patch server / community

- `GET /patches/:slug[@version]` → MMLisp snippet or FM voice JSON, each with
  author, license and version history; lineage through a `fork_of` field, so a
  patch can be forked and the derivation tree browsed.
- **Preview is in-browser synthesis only** — the chip emulator is already
  there, so no rendered audio is stored. Finished works link out (`demo_url`).
- Voice metadata carries identity, authorship and license, Cubase-style
  classification (category, collection, tags) and the technical fields a
  preview needs (chip, base note, polyphony).
- Infrastructure sketch: Cloudflare Pages + Workers + R2, with an `index.json`
  rebuilt on upload and filtered client-side. A metadata DB (D1) only when tag
  queries get slow, auth is needed, or the patch count passes thousands.

### PCM variant handling

A sample with natural variants (dry / compressed / reverb tail) ships as
separately named voices, with `fork_of` recording the shared origin. The later
option is one dry master plus a declarative `processing` chain per voice that
the server applies at build time — worth building when it buys FM/PCM balance
and consistent drum-kit levels without touching the master file.

### Multi-chip expansion

The IR layer is chip-agnostic; only the backend (MMB exporter + driver) is
chip-specific.

| Chip          | System                  | Type                            |
| ------------- | ----------------------- | ------------------------------- |
| YM2612        | Sega Mega Drive         | FM (OPN2) — current baseline    |
| YM2151        | arcade, X68000          | FM (OPM)                        |
| YM2413        | Sega Master System, MSX | FM (OPLL, ROM voices)           |
| SID 6581/8580 | Commodore 64            | analog multi-mode filter        |
| 2A03 / RP2A07 | NES / Famicom           | pulse + triangle + noise + DPCM |
| HuC6280       | PC Engine               | wavetable (32-byte waveforms)   |

Each chip needs its own target profile, register encoder and JS emulator.
